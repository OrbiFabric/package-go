# Import/export plans and verified hydration

`PlanImport` and `PlanExport` inspect one explicitly selected `SnapshotSource`, including Directory or ZIP. They create sealed `TransferPlan` state; `Summary()` returns an owned review copy, not editable authority. Planning has no Resolver or publication side effects. The plan includes the actual HEAD parent chain, every distinct historical ContentID (including HEAD and removed/moved files), checked extra objects, exact portable/raw file preservation, prospective entry/byte limits and the original offline completeness observation.

`TransferOptions.Facts` is mandatory Host fact selection. It receives owned exact control JSON/NDJSON bytes and the entire prospective entry inventory, including opaque extensions. The Host must approve privacy-safe facts and inspect opaque data through its authorized source; schema validation does not redact secrets. This API preserves all selected source bytes and offers no implicit removal or rewrite. Missing Complete memory or embedded evidence needs explicit upstream repair, not fabricated defaults. Existing wrong object hashes reject rather than falling back to a Resolver.

`ExecuteTransferDirectory` reopens the selected source, checks expected HEAD, revalidates history/objects/memory/evidence presence and compares an exact whole-tree raw-byte fingerprint with the plan. It repeats Host approval and stable observation checks before effects. Metadata/inodes are not portable identity; the operation fingerprint includes paths/kinds/sizes and raw file hashes, plus explicit unavailable-object observations. Plan review-copy and caller revision-map changes cannot alter private execution state. Changes after planning reject, including same-size payload edits with restored mtime.

Only explicitly missing objects invoke `ContentResolver`, once per ContentID. Each request has its expected digest/size and optional transient Host revision. The SDK rehashes/counts the complete incoming stream and closes it. A selected nonempty revision requires the matching response `Revision` and `ResolvedContent.CheckStable`, called after reading and close to confirm the same remote revision. Wrong hash/size/revision, missing stability support, late revision changes, read/close/callback errors and cancellation prevent publication. Without a Resolver, missing bytes remain an offline failure. The SDK does not fetch URLs, credentials, Providers or evidence statuses itself.

Hydration writes independent object bytes directly into isolated external pending output, with no permanent managed-store requirement or source mutation. The SDK copies every other file byte exactly, preserves empty folders, writes HEAD last inside isolation, seals output and reopens it through the same Directory/model/whole-history/all-object/memory/evidence-presence checks. `TransferResult.Output.HistoryCompleteness=FULL` describes those actual sealed bytes only; `Input` retains the original offline NOT_FULL/UNAVAILABLE observation. No signature mathematics or trust verdict is inferred from FULL; those dimensions stay independent.

`ExecuteTransferZIP` uses an unpublished temporary Directory transaction for the verified full tree, then writes ZIP into `ArtifactHost` pending output. It seals and reads back the actual artifact, verifies artifact hash/size, decodes through the bounded ZIP codec and compares every raw file with the verified staged tree. Both temporary tree and original source are closed/cleaned before final no-overwrite artifact publication. Importing a ZIP uses `NewZIPSource` and the same `PlanImport`/Directory execution; there is no legacy dispatcher or second protocol implementation.

`NewArtifactHost` and `NewFileArchiveSource` provide native Linux reference operations: component-anchored no-follow regular-file access, external random private pending files, byte limits, full artifact hash/descriptor stability, fsync and atomic no-replacement rename. Existing files/directories/links survive. Pending-only abort verifies the named inode before deletion and never removes a destination after a successful or uncertain move. Source and temporary/final destinations require explicit Host authorization and exclusion of hostile writers. Other platforms explicitly require safe Host implementations; compilation is not native runtime evidence.

Every failure returns an empty transfer result, including close/cleanup/uncertain-acknowledgement errors. `ErrPublicationUncertain` requires Host inspection/recovery; no automatic overwrite/retry follows. A process interruption can leave an isolated external pending file, which Host recovery must treat as unfinished. Artifact digests and Host revision pins never enter Version subjects or portable facts. This stage's coupled transfer proof is not a seven-level conformance certificate or producer freeze.
